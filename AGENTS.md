# Правила работы с lean-fns

## Хранение контекста

- Анализ, историю работ, принятые и отклонённые решения, результаты проверок, ошибки и следующие шаги хранить в базе Obsidian пользователя. Путь к базе брать из пользовательских инструкций среды.
- Использовать существующий раздел `utility-library`, обновлять связанные заметки вместо создания дубликатов.
- Перед продолжением работы читать соответствующие заметки и сверять их с фактическим состоянием проекта.
- Сохранять контекст после каждого значимого этапа; писать по-русски, указывать дату проверки и отличать подтверждённые сведения от предположений. После записи проверять содержимое файлов.
- В репозитории хранить исходники, тесты, конфигурацию, README и инструкции для работы: навыки, AGENTS.md и правила проекта. Не создавать здесь журналы выполненных работ, отчёты проверок, личные заметки и копии базы знаний.
- Не записывать в заметки секреты или избыточные служебные логи.

## Разработка

- Сохранять нулевые runtime-зависимости. Инструменты сборки и тестирования относятся к devDependencies.
- Реализация функций требует отдельного поручения; текущий этап ограничен настройкой проекта.
- Не обещать выигрыша в скорости или размере без воспроизводимых измерений.
- Версии инструментов и команды брать из package.json и lockfile; основная проверка — `pnpm check`.
- Выполнять проверки, соответствующие изменению. Для правок документации не запускать заново весь набор тестов без причины.

## Code review

- Использовать [requesting-code-review](.agents/skills/requesting-code-review/SKILL.md) для ревью готовых изменений кода по запросу пользователя, после завершения существенной реализации и перед merge. Анализ, планирование, статьи и отдельная установка навыка сами по себе не запускают reviewer.
- Оригинальные SKILL.md и code-reviewer.md сохранять без локальных правок.
- Основной Codex подготавливает входные данные, предусмотренные авторским шаблоном code-reviewer.md.
- Запускать одного reviewer со свежим контекстом через native-профиль [code-reviewer](.codex/agents/code-reviewer.toml), без передачи всей истории чата и без overrides модели или reasoning. Профиль задаёт gpt-6-astra/xhigh; имя обычного субагента не заменяет выбор native-профиля.
- Если клиент не позволяет выбрать профиль или подтвердить его загрузку, сообщить ограничение. Не подменять его обычным агентом и не объявлять ревью выполненным. Отсутствие reviewer не препятствует самостоятельной подготовке разрешённых изменений, но не заменяет требуемую проверку перед merge.
- Reviewer читает авторский code-reviewer.md; методику проверки и формат отчёта брать из него без дополнительных проектных инструкций для reviewer.
- Запрос только на ревью не разрешает исправления. В уже порученной реализации подтверждённые исправления входят в работу; внешний commit/push/merge требует соответствующего разрешения. Итог ревью и ограничения сохраняет основной Codex в Obsidian.

Пример запроса: «Используй requesting-code-review. Требования: <описание задачи>. Диапазон: <BASE_SHA>..<HEAD_SHA>».

## Внешние действия

- Перед отправкой или изменением данных во внешних сервисах требуется явное разрешение пользователя на конкретное действие и данные.
- Учитывать уже полученное разрешение в рамках согласованного действия; не запрашивать его повторно без изменения объёма.
- Локальное ведение Obsidian разрешено пользователем и не является разрешением на commit, push или публикацию.
